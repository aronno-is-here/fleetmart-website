ITEMS REQUIRING CODE CHANGES
================================================================================

FIX 1: Metadata format (payment.js line 133)
  Current:  metadata: JSON.stringify({ attemptId })
  Required: metadata: { attemptId }  (plain object)
  Reason:   Official docs show metadata as JSON object, not stringified.
            OpenAPI schema declares "format": "json" but all examples
            show plain objects.

FIX 2: Webhook handler must validate API key (payment.js line 301)
  Current:  No header validation
  Required: Check req.headers['rt-uddoktapay-api-key'] === UDDOKTAPAY_API_KEY
  Reason:   Official webhook docs explicitly require this.

FIX 3: Webhook handler must process full payload (payment.js line 303)
  Current:  const { invoice_id } = req.body  (only reads invoice_id)
  Required: Process full payment data: amount, status, metadata,
            transaction_id, payment_method, sender_number, etc.
  Reason:   Webhook sends the complete payment object.

FIX 4: Stock deduction error handling (payment.js line 265)
  Current:  .catch(() => {})  silently swallows failures
  Required: Log the error; consider admin notification
  Reason:   Silent failures make debugging impossible.

================================================================================
SECURITY ANALYSIS: Mark Completed Before Stock Deduction
================================================================================

Current order:
  1. attempt.status = 'completed'  (line 220)
  2. Order.create(...)             (line 230)
  3. Stock deduction loop          (line 260)
  4. attempt.orderId = orderId     (line 269)

Risk: If step 3 fails for some items, the order exists with
      paymentStatus: 'paid' but stock is not fully deducted.

Mitigation already present:
  - The $gte condition on stock prevents overselling
  - .catch(() => {}) prevents the entire flow from failing
  - Admin can manually reconcile

Verdict: MINOR RISK — acceptable for a Bangladeshi e-commerce site
         with manual fulfillment. The alternative (deduct stock before
         payment verification) creates a worse problem (stock held for
         unpaid orders).

================================================================================
PARTIAL PAYMENT SAFETY
================================================================================

amountToPay = Math.min(300, grand)

  - If grand < 300: customer pays full amount (no partial)
  - If grand >= 300: customer pays exactly 300 BDT
  - remainingAmount = grand - amountToPay (calculated correctly)
  - Server calculates these values, not the client

Verdict: SAFE
